# Vulkan/D3D12 대신 SDL3GPU를 선택한 이유

> **한 줄 요약**: 저수준 API의 복잡성을 SDL3GPU에 위임하여, 입대 전 한정된 시간 내에 엔진 아키텍처(RenderGraph/ECS) 설계에 집중하기 위한 전략적 선택.

---

## 1. 왜 SDL3GPU를 선택했는지?

프로젝트를 처음 시작할 당시, 내 그래픽스 API 지식은 사실상 전무했다. 기껏해야 대학교 프로젝트로 SDL2를 이용해 간단한 수박 게임을 만들거나, DirectX 11 튜토리얼을 따라 치며 화면에 삼각형 하나를 간신히 띄워본 것이 전부였다.

이런 나에게 현대적인 그래픽스 API의 **Command Buffer, Resource Barrier, PSO(Pipeline State Object)** 같은 개념은 외계어와 같았다. 하지만 **역설적으로 그 무지가 용기가 되었다.**

마침 내가 좋아하던 SDL의 최신 버전인 SDL3가 공개되었고, 그 안에 Vulkan과 D3D12를 하나로 묶는 `SDL3GPU`라는 미성숙하지만 매력적인 API가 포함되어 있었다. 남들이 이미 다 닦아놓은 DX11이나 Vulkan 튜토리얼을 답습하기보다, **"이왕 하는 김에 최신 기술을 직접 경험해보자"**는 생각으로 고민 없이 SDL3GPU를 선택했다.

---

## 2. 전략적 판단 근거

삼각형 하나 그리는 데 끙끙대던 초창기의 선택은, 결과적으로 내 그래픽스 지식을 비약적으로 끌어올려 준 **'신의 한 수'**가 되었다. 무모해 보였던 이 결정에는 세 가지 명확한 전략이 있었다.

1. **팬심과 신뢰**: SDL2를 써오며 느꼈던 API 설계에 대한 신뢰감이 컸다. 아직 미성숙한 단계였지만, `SDL3GPU`는 나 같은 뉴비가 복잡한 그래픽스 API를 직접 다루는 부담을 크게 줄여줄 것이라는 믿음이 있었다.
2. **선택과 집중**: Vulkan이나 D3D12를 직접 붙잡고 백엔드를 구현했다면, 아마 입대 전까지 삼각형 이상의 결과물을 보기 힘들었을 것이다. 플랫폼마다 다른 저수준 추상화라는 무거운 짐은 SDL3에게 던져버리고, 나는 **"RenderGraph 설계와 ECS 연동"**이라는 엔진 본연의 구조적 고민에 집중했다.
3. **복잡한 관리의 자동화**: 모던 API의 최대 난관인 **리소스 베리어(Resource Barrier) 추론과 메모리 수명 관리**를 SDL3GPU의 **사이클(Cycle)** 기능에 위임했다. 덕분에 동기화 지옥에서 벗어나 상위 레벨의 파이프라인 로직을 안전하게 구축할 수 있었다.

---

## 3. 검토한 대안들

| 대안 | 장점 | 단점 / 탈락 이유 |
| :--- | :--- | :--- |
| **Vulkan / D3D12 직접** | 최대 제어권, 오버헤드 없음 | 초보자가 직접 다루기엔 진입 장벽이 너무 높음, 플랫폼별 코드 분기 폭증. |
| **D3D12 직접** | Windows 환경 최적화 | 이식성 없음, 다른 플랫폼 지원 불가. |
| **-> SDL3GPU (채택)** | 단일 API로 다중 백엔드 지원 | 직접적인 저수준 제어에 제약이 있으나, **학습 곡선이 낮아 아키텍처 집중 가능.** |

---

## 4. 결과와 트레이드오프

**얻은 것:**

- 바닥부터 시작한 그래픽스 지식의 진입 장벽을 낮추고, 렌더링 아키텍처 설계에 집중할 수 있었음.
- SDL3GPU의 자동화 기능을 활용해 안정적인 리소스 동기화 달성.

**잃은 것 / 수용한 비용:**

- GPU 타임라인 세마포어 등 최하단 수준의 최적화 제어권 포기.
- 발전 중인 오픈소스 라이브러리의 버그를 직접 디버깅하며 대응해야 함.

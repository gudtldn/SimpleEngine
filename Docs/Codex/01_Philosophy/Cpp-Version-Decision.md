# C++ 표준 정책과 모듈(Modules), char8_t 철회 결정

> **한 줄 요약**: 최신 C++ 표준(C++23)을 적극 도입하되, 컴파일러와 툴체인 지원이 미숙하여 생산성을 깎아먹는 C++20 모듈(Modules)과 `char8_t`는 과감히 롤백했다.
---

## 1. 왜 최신 C++ 표준을 사용하는지?

프로젝트의 C++ 표준 방침은 아주 단순하다.
"**C++의 최신 기능을 사용하고, 직접 한계를 확인하기 위해서.**"
~~(말은 그럴듯 하게 했지만, 그냥 최신 C++ 기능을 남들보다 먼저 맛보고 싶어서 ㅋㅋ)~~

추후 C++26 컴파일러 지원이 성숙해지면 **정적 리플렉션(Reflection)** 도입을 위해 버전을 바로 올릴 계획이고, 상황에 따라 C++29까지도 열어두고 있다.

다만 실제로 엔진에 도입해보니 **"표준에서 사용할 수 있다고, 바로 적용해서 사용할 수 있는지?"** 는 완전 별개의 문제였다. 그중에서도 특히 C++20 모듈(Modules)과 `char8_t`는 굳이 써보겠다고 고집을 부리다가, 너무 불편해서 결국 철회했다.

---

## 2. 프로젝트에서 C++23 기능을 어떻게 활용하는지?

### 2.1. CMake 핵심 설정

```cmake
# Tools/CMake/SEDefaultOptions.cmake
target_compile_features(SE_DefaultOptions INTERFACE
    cxx_std_23
)

# MSVC: 비표준 확장 차단, 표준 전처리기 사용
target_compile_options(SE_DefaultOptions INTERFACE
    /permissive-
    /Zc:preprocessor
    /Zc:__cplusplus
)
```

### 2.2. 실제 사용하는 기능들 (C++20, 23)

- **`std::format`, `std::print, println`**: 커스텀 로깅 및 문자열 포맷팅에 사용.
- **C++20 코루틴 (`co_await`, `co_return`)**: JobSystem의 `JobTask<T>`에 적극 활용하여 비동기 처리 단순화.
- **`deducing this`, `std::forward_like**`: 중복되던 const/non-const 오버로딩 코드를 깔끔하게 정리하는 데 사용.
- **C++20 Concepts (`concept`, `requires`)**: 복잡한 SFINAE 기법을 직관적인 제약 조건으로 대체.
- **`std::unreachable`**: 컴파일러에게 최적화 힌트를 제공하고, 코드가 도달할 수 없는 경우를 명시할 때 사용.
- **`std::ranges` / View Composition**: 컨테이너 데이터를 파이프라인 형태로 처리할 때 활용.
- **`if consteval`, `constexpr` 확장**: 컴파일 타임 분기를 제어할 때 사용.

추가로 현재 엔진의 리플렉션 시스템은 `SE_CLASS`, `SE_ANNOTATION` 같은 매크로 기반으로 구현되어 있는데, 추후 컴파일러가 P2996 정적 리플렉션을 지원하게 되면 이 매크로들을 대부분 걷어낼 생각이다.

그래서 나중에 컴파일러가 성숙해졌을 때 껍데기만 쏙 벗겨내고 손쉽게 교체할 수 있도록, 처음부터 인터페이스와 구현 구조를 분리해서 설계해 두었다.

---

## 3. C++20 모듈(Modules) 도입 후 철회한 이유

### 3.1. 시도한 것

프로젝트 극 초기에 C++20 모듈(`import`, `export module`)을 도입했었다. 헤더 파싱 반복 비용을 제거하고, 전역 네임스페이스 오염을 차단하며, 빌드 속도 향상을 기대했다.

### 3.2. 부딪힌 문제들

1. **IDE 및 도구 지원 부실**: 당장 사용하기에는 **CMake나 clangd 같은 도구를 세팅하는 비용이 너무 컸다.** 특히 IntelliSense가 모듈 경계를 제대로 인식하지 못해 툭하면 빨간 줄을 뱉어내어 **개발 경험(DX)이 최악**이었다.

2. **순환 참조와 전방 선언의 제약**: 기존 헤더 방식에서는 전방 선언 몇 줄로 간단하게 끊어내던 의존성 사이클이, 모듈 환경에서는 빈번하게 충돌로 이어졌다. 모듈은 전방 선언 대신 완전한 정의를 요구하는 경우가 많았고, 일반 헤더에서는 쉬웠던 설계가 모듈에서는 구조를 통째로 뜯어고쳐야 하는 상황으로 번졌다.

3. **ThirdParty 생태계와의 불협화음**: SDL3, ImGui 등 필수 ThirdParty 라이브러리들은 당연히 모듈을 지원하지 않는다. 결국 모듈 파일 상단에 `global fragment`를 열고 기존 헤더를 감싸서 `#include` 해야 했는데, 이 과정에서 발생하는 보일러플레이트 코드와 매크로 유출 방어가 너무 번거로웠다.

### 3.3. 결론

모듈로 얻는 이점보다 구조를 억지로 끼워 맞추고 툴체인 버그와 싸우는 유지보수 비용이 명확히 컸다. 물론 내가 아직 모듈 기반 설계에 익숙하지 않은 탓도 있겠으나, 현재로서는 결국 전통적인 헤더 방식으로 복귀하는 것이 합리적이라고 판단했다. 향후 생태계가 성숙해지면 재도입을 검토하는 방향으로 변경했다.

## 4. `char8_t` 도입 후 철회한 이유

### 4.1. 시도한 것

프로젝트 초반, 엔진의 기본 문자열 타입을 `char8_t` 기반의 `std::u8string`으로 설정했다.
C++20에서 UTF-8 리터럴(`u8"..."`)의 타입이 `char8_t`로 바뀐 것을 활용하여, 타입 시스템 수준에서 UTF-8 문자열을 명시적으로 구분하고 강제하려는 의도였다.

### 4.2. 부딪힌 문제들

1. **ThirdParty 라이브러리 비호환**: `char8_t*`와 `char*` 사이에는 암묵적 변환이 허용되지 않아서 경계마다 `reinterpret_cast`가 필요한데, 정작 SDL3, ImGui, Assimp등 엔진이 의존하는 거의 모든 라이브러리는 여전히 `const char*`나 `std::string_view`를 인자로 받는다. 결과적으로 라이브러리 경계를 넘나들 때마다 쓸데없는 `reinterpret_cast`를 도배해야 했다.

2. **표준 라이브러리 지원 미비:** 외부 라이브러리만 문제인 게 아니었다. 정작 C++ 표준인 `std::filesystem::path`나 `std::format`조차 `char8_t` 지원에 나사가 빠져있어서, 표준 라이브러리를 쓰는 곳에서조차 강제 형변환 보일러플레이트가 늘어났다. 타입 안정성을 얻으려다가 코드 가독성이 박살 나는 주객전도가 발생했다.

### 4.3. 해결책

결국 MSVC의 `/utf-8` 플래그를 사용하여 소스 파일과 실행 파일 인코딩을 통째로 UTF-8로 고정해 버렸다. 결과적으로 일반 `char` / `std::string`이 사실상 UTF-8 문자열로 동작하게 되므로, 불편한 `char8_t`를 억지로 쓸 이유가 쓸 이유가 사라졌다.

```cmake
# MSVC
/utf-8  # 소스/실행 인코딩을 UTF-8로 고정

# GCC / Clang
-finput-charset=UTF-8
-fexec-charset=UTF-8
```

또한 추가로 현재는 내부적으로 `Array<char>`를 사용하는 커스텀 `String` 타입을 구축하여 사용 중이며, 실제 대소문자 변환 같은 복잡한 유니코드 처리는 **ICU4X**에 위임하여 처리하고 있다.

## 5. 결과와 트레이드오프

**얻은 것:**

- ThirdParty와의 `char` 호환성 완전 유지
- 모듈 관련 툴체인 이슈 없이 안정적인 빌드

**잃은 것 / 수용한 비용:**

- 모듈의 빌드 시간 단축 이점 없음 (PCH로 부분 보완)
- 타입 시스템에서 UTF-8 문자열을 명시적으로 구분할 수 없음 -> `char`을 UTF-8로 간주하는 컨벤션에 의존

**미해결 / 미래 과제:**

- C++26 P2996 정적 리플렉션 안정화 시 `SE_CLASS` / `SE_ANNOTATION` 매크로 대체
- 컴파일러 지원이 성숙하면 모듈 재도입 검토
- C++26 `#embed` 안정화 시 셰이더 바이트코드 번들링에 활용 가능
